# FitKeep Agent 协同开发交接说明

本文是 FitKeep 双端 Agent 的开发交接入口。执行者先阅读[开发计划](superpowers/plans/2026-09-29-fitkeep-dual-agent-development.md)、[可行性报告](../agent-plugin/可行性与架构分析报告-2026-09-29.md)、对应 Task 的验收条目和自己分支的最新提交。本文件说明协作权限；它不表示任何 Task 已启动、已完成或已获生产发布授权。

## 产品边界

- Agent 只通过 FitKeep Java 的登记接口下达业务操作。Java 负责当前身份、权限、业务规则、数据库、审批执行和返回给现有页面的数据。
- 用户端与管理员端是两套隔离的 Agent 能力。可共用模型运行代码，但工具目录、会话和审计不能混用。
- 用户端可直接查询当前用户的数据和已发布课程；写入先展示内容并取得用户确认。打开课程由 Java 返回固定路由名和课程 ID，现有页面跳转。
- 管理员端对涉及用户或平台数据的每一次查询、增加、修改和删除都先显示具体审批卡，管理员批准后由 Java 执行。
- 唯一预授权自治例外是社区监管：规则明确的不当内容仅自动隐藏并交管理员事后复核；不确定内容只待审。评论在具备可恢复隐藏接口前不能自动隐藏。
- 模型无权直连 MySQL、执行任意 HTTP/SQL/Shell、读取密钥、生成可执行 URL 或扩大自身工具权限。

## 三方角色与最终决定权

| 角色 | 主责与可执行工作 | 不得自行决定或执行 |

| **MiniMax Code：Java 后端与 Agent 服务执行工程师** | 实现 Spring Boot 业务接口、权限修复、类型化工具、审批/幂等/审计、MyBatis/SQL 变更、独立模型服务、社区监管后端和相应自动化测试；向 ZCode 提供冻结接口的模拟响应与错误示例。 | 不改静态用户/管理页面，不单方放宽权限、降低审批级别、自动执行数据库迁移或生产部署，不把普通管理员接口当作监管服务的万能入口，不宣布自己交付“已验收”。 |

用户拥有产品范围、体验和是否发布的最终选择权；Codex 负责在该范围内做技术决策和审核。Codex 的代码审核与产品运行时的管理员逐项审批是两件事：前者审开发交付，后者授权真实用户/平台数据操作。

不要根据 ZCode 或 MiniMax Code 的界面名称猜测底层模型版本。若模型版本影响排查，交接证据记录实际返回的 model ID，不记录密钥、提示词中的个人数据或 Token。

## 任务与文件所有权

Task 编号、依赖、产物和验收条件以[开发计划](superpowers/plans/2026-09-29-fitkeep-dual-agent-development.md)为准。Codex 拥有 `docs/agent-capability-matrix.md`、`docs/agent-contract.md`、开发计划、本文和最终集成记录。MiniMax Code 拥有 `server/src/main/java/**`、`server/src/test/java/**`、`server/src/main/resources/mapper/**`、`server/src/main/resources/init.sql`、`ops/db/**` 与 `agent-plugin/service/**`。ZCode 拥有 `server/src/main/resources/static/user/**`、`static/admin/**` 及其页面验证文件。执行者各自拥有自己 Task 的 `docs/verification/task-<编号>.md`。

所有目录都可只读检查，但同一时刻同一文件只能有一个写入 Owner。`server/src/main/resources/application.properties`、`server/pom.xml`、`.github/workflows/**` 和现有 `agent-plugin/README.md` 属跨端文件；谁要改，先由 Codex 指定 Owner 和兼容方案。若执行中发现计划缺口，先提交问题和建议，不自行越界改另一方文件。

当前仓库有未提交 Agent MVP 和其他本地工作。Task 00 前任何人不得假设 `origin/main` 已包含本地草稿，也不得清理、覆盖或顺手提交这些文件。Codex 先记录基线、确定保留内容和落地分支，再把可复现起点交给执行者。

## 分支、集成和部署

1. 每个执行 Task 使用独立工作树和分支。推荐 `agent/minimax-task-<编号>-<短名>` 与 `agent/zcode-task-<编号>-<短名>`；Codex 集成分支使用 `codex/` 前缀。执行者可推自己的任务分支，但不能直接推 `main`、强推、硬重置或修改另一方工作树。
2. 跨端并行前由 Codex 冻结 DTO、工具名、错误码、审批状态、导航路由和版本。MiniMax Code 与 ZCode 只对这个契约实现；任何一方需改变公共字段时先停下并提出契约变更。
3. GitHub Actions 已设置 `main` 的 `server/**` 改动自动部署 VPS。任务分支的测试与推送不是生产发布；`main` 集成会触发线上发布。Codex 在独立验收与发布范围确认后才把适当变更推进 `main`。Agent 独立服务还需要自己的部署/回滚步骤，现有 JAR 工作流不会自动发布它。
4. 数据库变更提交可审查的版本化 SQL、测试和回滚说明。执行者不得自行在生产库运行。生产配置、DeepSeek Key、SSH 私钥、用户数据和 Token 不进仓库、交接文档或测试日志。
5. Task 合入或废弃后，Codex 清理不再使用的临时工作树并保留可追溯的提交；有仍在运行的进程或未转移工作时先处理它们。

## 每个 Task 的执行与交接

执行者在自己的 Task 证据文件中记录以下信息；本文只维护当前状态和下一个依赖，不粘贴长日志。

1. 状态：`未开始 / 开发中 / 待 Codex 验收 / 待用户验收 / 用户已验收 / 受阻`，以及基线分支和提交。
2. 实际完成范围与明确未完成范围，对照开发计划的验收条目。
3. 修改文件清单、接口/Schema/SQL 变化和兼容性影响。
4. 新业务行为的失败测试、修复后的聚焦测试及全量验证命令和结果；没有运行的检查写“未运行”。
5. 模拟模型、模拟 API、测试库、真实 Java/MySQL、真实 DeepSeek、真实浏览器分别标记证据级别。真实回执需同时核查业务数据或页面最终状态。
6. 安全检查：跨角色、跨用户、未审批、重复确认、过期动作、恶意字段、模型返回不可信内容、服务故障。与当前 Task 无关的项注明原因。
7. 已知限制、未提交文件、待 Codex 决策点、交付提交号与下一位执行者的入口。

交付模板：

```text
Task：
基线与分支：
状态：待 Codex 验收
实现与未实现：
接口/文件/数据库变化：
RED 测试与结果：
GREEN 测试与结果：
真实联调证据或未运行原因：
安全边界与已知限制：
提交号及下一步：
```

MiniMax Code 不能因为 `mvn verify` 通过就宣称真实模型与页面完成。ZCode 不能因为静态页面或 Mock 工作就宣称数据库已写入。两端都不能仅凭 Agent 返回“成功”断定业务成功；需要 Java API、数据库或实际页面状态的独立证据。

## Codex 的验收流程

Codex 收到 `待 Codex 验收` 交付后，依次检查需求和冻结契约、文件 Owner、安全边界、源码 diff、失败测试是否真实复现、修复后测试、相关全量回归、需要的真实 Java/API/页面证据和文档一致性。发现问题则保留 Task 在待整改状态，给出可复现条件；修复后重新验收。跨端 Task 只有两端的公共契约和真实联调都通过，才标为技术验收通过。

每个 Task 都有两道连续门禁：Codex 先完成独立技术验收并给出可查看的代码/页面、测试方法、实际结果与已知限制；随后状态改为`待用户验收`，由用户亲自检查并明确确认。**收到用户对该 Task 的验收确认前，不开始依赖它的下一 Task，也不以 Codex 技术验收替代用户验收。** 用户提出问题则留在当前 Task 修复、复验并再次交用户确认。技术验收通过和用户验收均不等于生产发布。
